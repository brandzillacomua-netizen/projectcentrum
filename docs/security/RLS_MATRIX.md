# CENTRUM MES — матриця доступу до даних

Дата фіксації: 2026-09-12.

## Базова модель довіри

| Суб'єкт | Прямий доступ до таблиць | RPC | Умова |
|---|---|---|---|
| `anon` | Заборонено до всіх таблиць `public` | Лише `rpc_public_machine_call_context` і `rpc_public_create_machine_call` | Валідний UUID верстата, дозволена роль виклику, серверна валідація працівника, дедуплікація і ліміт |
| `authenticated` | Тільки через table grants + RLS | Явно дозволені виробничі RPC | JWT має бути прив'язаний до `system_users.auth_user_id` |
| `service_role` | Службовий контур | Службові RPC | Ключ ніколи не передається браузеру |
| Власник БД | Міграції та аварійне адміністрування | Усі | Тільки контрольований адміністративний канал |

## Публічний QR-виклик

| Ресурс | Читання | Створення | Зміна | Видалення |
|---|---|---|---|---|
| `machines` | Через контекстний RPC, лише 6 безпечних полів | — | — | — |
| `system_users` | Через контекстний RPC, лише ім'я, посада й допустимі ролі виклику | — | — | — |
| `machine_calls` | Через контекстний RPC, лише pending ID/роль/час конкретного верстата | Через атомарний RPC | Заборонено | Заборонено |

`rpc_public_create_machine_call` приймає тільки `master`, `engineer` або `quality`, перевіряє верстат і обраного працівника, очищує ім'я оператора, не створює другий активний виклик тієї самої ролі та обмежує частоту.

## Авторизований контур machine calls

| Дія | Хто має право | Технічний контроль |
|---|---|---|
| Перегляд | Будь-який прив'язаний MES-користувач | `mes_current_system_user_id()` |
| Створення | Виробничий клієнт через єдиний RPC | Серверна валідація RPC |
| Закриття | Майстер, бригадир, інженер, ВКЯ, обладнання, адміністратор, директор/начальник | RLS + дозвіл UPDATE лише для `status`, `resolved_at`, `resolved_by` |
| Видалення | Ніхто з браузера | Немає grant/policy |

## Контроль регресій

- `npm run audit:anon` перевіряє всі таблиці, які використовує клієнт, не виводячи їхні дані.
- `npm run security:access-contract` звіряє всі прямі клієнтські звернення до таблиць із затвердженим baseline. Нова таблиця, новий тип операції або новий динамічний доступ зупиняє CI до окремого security review.
- `npm run security:rls` забороняє нові анонімні `FOR ALL`, мутуючі table grants і небезпечні `SECURITY DEFINER` без фіксованого `search_path`.
- Після contract/lockdown міграцій очікуваний результат: **0 таблиць із доступним анонімному користувачу рядком**.
- Будь-який новий публічний сценарій оформлюється окремим мінімальним RPC і додається до allow-list лише після threat review.

## Фактичний baseline авторизованого клієнта

Статичний аудит клієнта на дату фіксації виявив **55 таблиць**, **1164 literal call sites** та **7 контрольованих динамічних call sites**. Із 55 таблиць клієнт виконує операції запису у 46.

Найбільша концентрація прямого запису:

| Таблиця | Місць запису | Ризик обмеження одним релізом |
|---|---:|---|
| `inventory` | 110 | Критичний: склад, резерви, передачі між етапами |
| `work_cards` | 88 | Критичний: основний виробничий workflow |
| `material_requests` | 83 | Критичний: забезпечення виробництва |
| `tasks` | 60 | Високий: операційні задачі багатьох модулів |
| `work_card_history` | 60 | Критичний: аудит руху карток і звітність |

Повний машинозчитуваний перелік міститься у `security/client-data-access-baseline.json`.

Важливо: baseline **не є дозволом на рівні БД** і не замінює RLS. Це запобіжник, який стабілізує поточний контракт перед поетапним звуженням прав у production.

## Безпечний порядок впровадження authenticated RBAC

1. **Хвиля A — спостереження і контракт (виконано).** Зафіксувати таблиці та операції, підключити блокування регресій у CI. Ризик для production: низький.
2. **Хвиля B — єдина серверна ідентичність (виконано 2026-09-12).** `npm run audit:auth-bindings` перевіряє каталог через звичайний JWT, а `supabase/diagnostics/auth_identity_binding_preflight.sql` звіряє `system_users` з внутрішнім `auth.users`. Production preflight: 139 MES-користувачів, 139 прив'язаних, 0 пропущених, 0 сиріт, 0 конфліктів metadata, 0 дублів; статус `PASS`.
3. **Хвиля C — довідники та ізольовані модулі (C1 застосовано 2026-09-12).** `system_configs`, `scrap_reasons`, `vkya_restoration_stages` переведено на least-privilege grants і рольові write-policy; production postcondition `PASS` з нульовими відхиленнями. `nomenclature_prices` виключено, оскільки таблиця відсутня у production. Точний rollback збережено за runbook `docs/security/WAVE_C1_CATALOG_RBAC.md`.
4. **Хвиля D — CRM, чат, обладнання, задачі.** Вводити політики по одному домену, із журналюванням відмов RLS і canary-групою користувачів. Ризик: середній/високий.
5. **Хвиля E — виробниче ядро.** `orders`, `inventory`, `material_requests`, `work_cards`, `work_card_history` переводити лише після E2E-матриці ролей і перевіреного відновлення БД. Ризик: критичний.

Кожна хвиля проходить: preflight → staging → рольові позитивні й негативні тести → резервна копія → canary → production → postcondition → період спостереження. Наступна хвиля не починається, доки попередня не має підтвердженого rollback.

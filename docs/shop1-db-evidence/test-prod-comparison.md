# Цех №1: порівняння TEST і PROD

Дата: 2026-09-09. Джерела: test-preflight-2026-09-09.json та prod-preflight-2026-09-09.json. Другий файл користувача прийнято як TEST за контекстом попереднього запиту; ідентифікатор Supabase-проєкту не входить до експорту.

## Висновок

TEST суттєво відрізняється від PROD у логіці складського обліку. Успішний ручний сценарій на поточному TEST не доводить правильність списання на PROD. Перед перевіркою нового завершення розкрою потрібно відтворити релевантні production-залежності у тестовому середовищі. Повний автоматичний перенос усіх міграцій не підходить: локальний аудит виявив міграцію масового обнулення резервів.

| Розділ вибірки | PROD | TEST |
|---|---:|---:|
| Колонки | 125 | 109 |
| Індекси | 48 | 13 |
| Політики | 6 | 4 |
| Користувацькі тригери | 2 | 1 |
| Функції з п'яти запитаних імен | 5 | 0 |
| Обмеження | 14 | 11 |

## Відмінності, що впливають на перевірку

1. У TEST немає тригера material_requests.trg_reconcile_inventory_reserve і функції reconcile_inventory_reserve. У PROD зміна запиту автоматично перераховує резерв; TEST не відтворює цю поведінку.
2. У TEST немає жодної з п'яти функцій, які шукав preflight: rpc_transition_work_card_atomic, rpc_deduct_inventory_atomic, rpc_increment_inventory_stock, register_cutter_usage, reconcile_inventory_reserve. Це не означає відсутності всіх функцій БД. Клієнтські сервіси atomicCardTransitionService.js та atomicInventoryService.js містять резервні шляхи виконання при помилці RPC, тому однаковий вигляд інтерфейсу не свідчить про однаковий серверний шлях.
3. У TEST не повернулися колонки cutter_usage_events і cutter_restoration_batches. Їх відсутність у вибірці означає, що таблиці відсутні або недоступні ролі експорту; потрібно врахувати перед підключенням обліку/відновлення фрез.
4. TEST має політики ALL з qual=true/with_check=true для чотирьох таблиць; PROD використовує verify_app_secret(), а також окремі політики work_cards. Стан увімкнення RLS і права функцій не входять до експорту. Копіювати тестові політики в PROD не можна.
5. work_cards.machine_id: TEST text, PROD uuid; tasks.batch_index: TEST text, PROD integer; tasks.planned_deadline: TEST text, PROD timestamp; work_card_history.started_at: TEST text, PROD timestamptz. Є відмінності integer/bigint/numeric і NULL/default. Нова функція має перевіряти цілі кількості та використовувати сумісні спільні колонки.
6. У TEST є work_cards.updated_at, у PROD немає. operator відсутній в обох вибірках, є operator_name. Поточну production-функцію переходу, що використовує operator та updated_at, не слід копіювати в TEST без виправлення.
7. inventory.warehouse за замовчуванням: TEST production, PROD operational. Нові складські записи повинні задавати склад явно.
8. Відрізняються зовнішні ключі та дії видалення. Наприклад, видалення карти каскадно видаляє її material_requests у PROD, а в TEST обнуляє card_id. TEST також не має production-індексів унікальності inventory. Тест створення резерву має враховувати ці обмеження.

## Порядок інтеграції

1. Підготувати окремий пакет сумісності TEST для потрібних складських залежностей із перевірками структури, прав та наявних даних. Не змінювати типи існуючих колонок автоматично і не переносити несправну стару RPC.
2. Реалізувати новий серверний шлях окремими таблицями/функціями, з вимкненим увімкненням для нових нарядів. Зберегти версію обліку на наряді: вимкнення загального прапорця не повинно повертати вже переведені карти старому списанню.
3. Зв'язати листові запити з нарядом, а виділений резерв фрез і листів — із конкретною картою та inventory_id. Підтримувати material_requests як джерело поточного перерахунку резерву, доки його власника не змінено узгоджено.
4. Завершення розкрою: в одній транзакції перевірити стадію та виділення, заблокувати записи у сталому порядку, зменшити листи рівно на кількість карти, фрези за фактом, зняти повний резерв фрез цієї карти, записати журнал, історію та перевести карту в буфер. Помилка повинна відкотити всю операцію. Повтор не списує вдруге. Новий шлях не має клієнтського fallback.
5. Серверно забезпечити три погодження перед генерацією. Зберегти дизайн і виробничий маршрут. Окремо врахувати повний брак та старі шляхи confirmBuffer/offline.
6. На TEST перевірити 15−3=12 під ще не створені карти, дві карти одночасно, повтор після таймауту, помилку посеред транзакції, два матеріали, факт фрез 0/1 із резерву 2, перевищення резерву та наступні стадії без повторного списання. Перевірка повинна явно підтверджувати виклик нового серверного шляху.

## Стан робіт

Обидва експорти збережено та порівняно. Аналіз не виконував запитів до БД і не змінював робочий інтерфейс. Пакет сумісності, серверна транзакція та їх інтеграційні перевірки ще не реалізовані; ці файли не є готовою міграцією.

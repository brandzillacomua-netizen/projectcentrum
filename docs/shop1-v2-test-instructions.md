# Цех №1: серверний пакет для TEST

## Що готово

Пакет `supabase/shop1-review/001_inventory_v2_candidate.sql` — окремий кандидат для перевірки. Він не входить до автоматичних міграцій. Встановлення створює приватні таблиці обліку, чотири серверні команди й захист керованих карт/запитів. Наявні залишки та запити встановлення не змінює. Обидва серверні прапорці початково вимкнені; доступ до команд для anon, authenticated і service_role відкликаний.

Робочі екрани не імпортують новий адаптер. Поточна production-поведінка ще не виправлена цим пакетом. Дизайн і маршрут не редагувалися.

Команди:

- `shop1_v2_reserve_sheets(task_id)` резервує всі явно визначені листові запити нового наряду один раз. Фізичний залишок незмінний. Видача повна; часткова або неоднозначна видача відхиляється. Погодження складу ставиться після успішного резервування, погодження інженера й директора не змінюються.
- `shop1_v2_enroll(task_id)` — адміністративний шлях прийняття вже повністю зарезервованого й погодженого нового наряду без жодної карти. Не створює резерв повторно. Не використовувати як масове перенесення старих нарядів.
- `shop1_v2_create_cards(task_id,batch_key,cards)` перевіряє три повні погодження, створює карти та їх явні розподіли резерву в одній транзакції. Повтор із тим самим ключем повертає ті самі ID; зміна даних із тим самим ключем відхиляється. Повторних запитів листів немає. Запити фрез мають бути вже видані на цей наряд.
- `shop1_v2_complete_cutting(...)` списує листи за зафіксованим розподілом карти; фрези — за фактом, звільняючи весь виділений цій карті резерв. Разом записує рухи, історію, використання/відновлення фрез, брак і перехід у буфер. Будь-яка помилка відкочує всю операцію. Повтор із тими самими фактами не змінює склад.

Для фрез потрібна реальна `register_cutter_usage(uuid,jsonb,bigint,text,jsonb)` та її залежності. Якщо її немає, позитивний факт фрез зупиняє й відкочує всю транзакцію. Для браку потрібен явний рядок складу `scrap_ready` цієї номенклатури в `operational` без власника. Функція не обирає випадковий рядок і не створює його автоматично.

## Що вже перевірено локально

`node scripts/check-shop1-database.mjs` виконує 124 перевірки в ізольованому PostgreSQL/PGlite. Він відтворює колонки обох наданих схем; для варіанта PROD використовує фактичне визначення тригера резервів із експорту. Перевіряє також сам файл `002_test_smoke_rollback.sql` і відсутність даних після його відкату.

Перевірені одноразове резервування, три погодження, 15−3=12 під майбутні карти, чужий резерв, два матеріали, повтори, помилки історії, відсутня залежність відновлення, факт фрез 1 із 2 та 0 із 2, відкат записів відновлення, частковий/повний брак, неправильний склад браку, заборона старому шляху завершувати керовану карту, права на нові RPC та робота звичайних карт під роллю anon.

Використовується справжнє визначення production-функції `register_cutter_usage`, а її класифікатор `is_faceting_cutter` у локальному тесті замінено функцією, що повертає true. Колонки таблиць відновлення взяті з PROD. Повні зовнішні ключі до інших модулів, реальні RLS, права й інші тригери локальний тест не відтворює. PGlite виконує запити послідовно: перевірки кількох конкурентних сесій ще немає.

`npx vitest run tests/shop1InventoryCommands.test.mjs` — 6 перевірок адаптера: використання переданого клієнта, точні факти, відсутність повторного/резервного запису при помилці, валідація кількостей і невизначеної відповіді.

`node scripts/check-shop1-phase01.mjs` — попередні 10 перевірок розрахункового контракту також пройшли. Перевірка цілісності чинних міграцій пройшла з попередженням про порядок наявного файла `20260706_production_statistics.sql`. Новий кандидат перевірено виконанням у локальному PostgreSQL, він не сканується загальним валідатором міграцій.

Для повторення локальних SQL-тестів потрібен окремий тестовий рушій:

```powershell
npm install --prefix tmp/shop1-db-check --no-audit --no-fund --ignore-scripts @electric-sql/pglite@0.3.14
node scripts/check-shop1-database.mjs
```

Основний package.json і залежності застосунку не змінено. Локальні тести не підключаються до віддалених БД.

## Перед підключенням до екранів

1. Перевірити багатосесійні блокування/повтори на TEST із production-подібними тригерами, обмеженнями та авторизацією. Пакет наразі серіалізує свої команди спільним advisory lock; це консервативний початковий варіант, не перевірка пропускної здатності.
2. Перевірити справжні залежності відновлення фрез на TEST. Поточний віддалений smoke навмисно перевіряє лише листи й не потребує відсутніх таблиць фрез.
3. Узгодити серверну перевірку прав користувача для кожної команди, а потім видавати лише потрібні EXECUTE. Не копіювати permissive TEST-політики на PROD.
4. Підключити новий шлях за незмінною версією наряду: складська видача, генерація та її запити фрез, звичайне завершення, повний брак, confirmBuffer і offline-черга. Врахувати, що чинна генерація надсилає запит фрез після створення карт, а новий контракт потребує виданого резерву до їх розподілу. Потрібен узгоджений проміжний стан/окрема команда виділення фрез, а не випадковий підбір за назвою.
5. Закрити обхід нових гарантій старими inventory-writer для спільних складських рядків. Приватний журнал і захист material_requests не усувають старий прямий RPC, що може окремо змінити фізичний склад. Тому права браузеру та production-cohort поки не вмикаються.
6. Лише після цього готувати окрему production-міграцію й увімкнення для нових нарядів. Автоматичного backfill та загального migration push у цьому пакеті немає.

## Пауза / відкат

Після встановлення та smoke обидва прапорці залишаються false, керованих нарядів не залишається. Зберегти цей стан достатньо для поточного етапу.

Для паузи адміністративних випробувань:

```sql
UPDATE shop1_v2.settings SET accept_new_tasks=false, completion_enabled=false WHERE id;
```

Вимкнення `accept_new_tasks` зупиняє прийняття нових нарядів; `completion_enabled` — нову генерацію та завершення. Повтор уже підтвердженої команди повертає її результат. Версія прийнятого наряду й захист записів зберігаються: вимкнення прапорців не переводить його на старе списання. Не видаляти populated схему/журнал і не обнуляти резерви для відкату.

## 1. Поточний стан системи (Від А до Я)

### 1.1. Високорівнева топологія та рух даних

Поточна архітектура системи CENTRUM MES v2.0 побудована за дволанковою гібридною схемою (Client-Heavy SPA + Edge Gateway + DB-Centric Backend) із проміжним інфраструктурним захисним екраном.

Мережевий та транзакційний ланцюжок:

[ Планшети / Термінали Цехів ] (React 19 + Offline Queue + TanStack Virtual)
       │
       │ HTTP/2 / WebSockets (Strict Bearer JWT)
       ▼
[ Cloudflare Enterprise Edge Gateway ] (WAF, Rate Limit, Origin Masking)
       │
       │ Encrypted TLS Tunnel (Gateway -> Supabase Origin)
       ▼
[ Supabase Managed PostgreSQL 15+ ]
  ├── API Layer: PostgREST Engine (GoTrue JWT Validation)
  ├── Concurrency Isolation: Operational Pool (6) / Analytical Pool (2)
  ├── Core Logic: Atomic PL/pgSQL RPCs + FSM v3 (SELECT ... FOR UPDATE)
  └── Persistence: Range Partitioned DB (work_card_history BY MONTH)

1. Точка входу та мережевий трафік:
Усі HTTP-запити та WebSocket-з'єднання з цехових планшетів спрямовуються через Cloudflare Enterprise Edge Gateway Worker. Оригінальний Supabase Origin повністю прихований за reverse proxy. Gateway виконує термінацію CORS, первинне фільтрування DDoS та пропуск WebSocket-запитів Realtime (Upgrade: websocket).

2. Ізоляція та локалізація бізнес-логіки:
Бізнес-логіка критичних транзакцій (зміна статусів робочих карток, списання матеріалів зі складу, оприбуткування готової продукції, фіксація браку) повністю винесена на рівень бази даних (PostgreSQL PL/pgSQL RPC). Клієнтський застосунок React 19 виконує роль екрану візуалізації та локального контролера офлайн-черги дій.

3. Синхронізація стану (Realtime State Propagation):
Зміна станів цехових карток транслюється через Supabase Realtime (WebSockets) із використанням скоупованих каналів (mes-primary, mes-secondary) та буферизатора wsBatcher (вікно затримки 150 мс).

---

### 1.2. Функціональні ролі модулів та сервісів

* Cloudflare Gateway: Reverse Proxy / WAF / Router. Маскування IP, DDoS protection, WAF, CORS normalization.
* GoTrue Auth Service: Identity & Access Management (IAM). Валідація JWT (ES256/HS256), інвалідація сесій, bcrypt хешування паролів (salt factor 8).
* FSM v3 (RPC Transition): Скінченний автомат переходів карток. rpc_transition_work_card_atomic: Песимістичне блокування FOR UPDATE, idempotency checking, атомарний запис у партиції.
* Inventory Deduct/Inc: Транзакційний складський облік. rpc_atomic_inventory_deduction, rpc_atomic_inventory_increment: Перевірка від'ємних залишків та атомарні зміни в єдиній транзакції PostgreSQL.
* Offline Queue Engine: Офлайн-стійкість клієнтів. offlineQueueService: Буферизація дій робітників у localStorage/IndexedDB при обриві Wi-Fi, хронологічний реплей через offlineProcessor.
* TimeSync Service: Коригування клієнтського дрифту. TimeSync: Коригування годинника клієнта за заголовоком Date HTTP-відповіді сервера (мілісекундна точність).

## 2. Аналіз використаних методів та рішень

### 2.1. Cloudflare Edge Gateway (Origin Masking)
* Проблема: Пряма публікація Supabase URL створює загрозу прямої атаки на PostgREST/GoTrue API, сканування портів та вичерпання лімітів запитів.
* Інженерне рішення: Reverse Proxy на Cloudflare Workers з блокуванням прямого доступу до Supabase Origin.
* Аргументація: Забезпечує маскування IP-адреси БД, централізоване керування CORS-політиками без перебудови схеми Postgres, а також відсікання неавторизованого трафіку на edge-серверах до того, як він досягне бази даних.

### 2.2. Native GoTrue JWT та відмова від Static Secrets (x-mes-secret)
* Проблема: Використання статичного секрету в заголовках HTTP створює витік прав при компрометації трафіку або Reverse Engineering клієнтського JS-коду.
* Інженерне рішення: 100% перехід на персональні JWT-токени (auth.users), вирізання x-mes-secret, санітизація пам'яті клієнта (useAuth.js) та REVOKE SELECT (password) ON system_users.
* Аргументація: Реалізує принцип Zero Trust. Кожен SQL-запит виконується з контекстом auth.uid(). Жоден стачний пароль чи секрет не передається у відкритому вигляді.

### 2.3. Секціонування таблиць (Range Partitioning BY MONTH)
* Проблема: Деградація швидкодії індексів та запитів SELECT при зростанні таблиці work_card_history понад 1 000 000+ записів.
* Інженерне рішення: Секціонування work_card_history за діапазоном дати (RANGE (created_at)). Налаштовано publish_via_partition_root = true.
* Аргументація: Скорочує розмір індексів (B-Tree) для поточного місяця, локалізує операції запису в малій партиції (work_card_history_2026_09) та дозволяє миттєво ротувати/архівувати старі дані без виконання важких операцій DELETE (замість цього використовується DROP/DETACH PARTITION).

### 2.4. Атомарний FSM v3 та песимістичне блокування (SELECT FOR UPDATE)
* Проблема: Стан гонитви (Race Condition), коли два оператори або два сканери одночасно сканують один і той самий штрихкод, призводячи до дублювання переходів статусу.
* Інженерне рішення: Атомарна RPC-процедура rpc_transition_work_card_atomic із песимістичним блокуванням рядка SELECT ... FOR UPDATE та перевіркою ключів ідемпотентності (p_idempotency_key).
* Аргументація: Гарантує строгий рівень ізоляції ACID. Другий паралельний запит блокується чеканням звільнення блокування рядка і відхиляється через перевірку FSM-статусу.

### 2.5. Ізоляція пулів з'єднань (Read Concurrency Isolation)
* Проблема: Важкі аналітичні звіти директора блокують пули з'єднань PostgreSQL, викликаючи затримки (latency) на цехових терміналах операторів.
* Інженерне рішення: Фізичне розділення пулів: SUPABASE_OPERATIONAL_CONCURRENCY = 6 (операційні термінали цеху) та SUPABASE_ANALYTICAL_CONCURRENCY = 2 (аналітичні звіти).
* Аргументація: Гарантує прогнозований SLA (< 15 мс) для цехових сканерів незалежно від обсягу аналітичних вибірок керівництва.

## 3. Критична оцінка (Trade-offs)

### 3.1. Компроміси архітектурних рішень (Чим довелося пожертвувати)

1. Складність підтримки та дебагінгу (DB-Centric Logic Overhead):
Винесення бізнес-логіки в SQL/PL/pgSQL RPC усунуло мережевий лаг, але суттєво ускладнило розробку. Рефакторинг процедур вимагає написання SQL-міграцій (наразі 76+ файлів), а дебагінг помилок у SQL-процедурах складніший за дебагінг у Node.js/Go.

2. Залежність від Vendor/Managed Infrastructure:
Платформа прив'язана до специфічних механізмів Supabase (GoTrue, PostgREST, Supabase Realtime). Перенесення системи на чистовий self-hosted PostgreSQL вимагатиме розгортання власного Auth-сервісу та WebSocket-сервера.

3. Обмежена гнучкість офлайн-черги дій:
Буферизація дій оператора при збоях мережі (offlineQueueService) гарантує доставку, але створює ризик відхилення дії при реплеї, якщо стан бази даних на сервері змінився за час відсутності зв'язку (наприклад, картку скасував диспетчер).

---

### 3.2. Вузькі місця (Bottlenecks) при пікових навантаженнях

1. Fan-out WebSocket з'єднань (Realtime Bottleneck):
При масовому зростанні кількості одночасних планшетів (понад 200+ пристроїв) масова трансляція подій карток створює пікове навантаження на процесор Supabase Realtime Engine. Рекомендація: посилення скоупінгу топіків (підписка лише на події конкретного цеху/верстата).

2. Адміністрування партицій PostgreSQL:
Секціонування за датами вимагає наявності майбутніх партицій. Якщо на початку місяця партицію (наприклад, work_card_history_2026_10) не буде створено автоматично, транзакції запису дій цеху впадуть з помилкою відсутності секції. Рекомендація: впровадження автоматичного pg_cron скрипта.

3. Ліміти пам'яті цехових планшетів (Client-side memory leak hazard):
При тривалій роботі без перезавантаження сторінки (24/7 зміни) накопичення логів та підписок у пам'яті браузера планшета може призвести до падіння вкладки Chrome через недостатність RAM.

## 4. Ризики та технічний борг

### 4.1. Аналіз ризиків та Потенційні точки відмови (Single Points of Failure)

1. SPOF 1: Єдиний інстанс БД Supabase (Single Primary Region)
Відсутність мульти-регіональної реплікації гарячого резерву (Hot Standby). При збої в дата-центрі провайдера Supabase або повній недоступності регіону API системи повністю припиняє обробку нових транзакцій.

2. SPOF 2: Залежність від заблокованого буфера Sentry DSN
Логер sentryLogger.js наразі працює у режимі локального кільцевого буфера (50 записів) в консолі браузера. Відсутній зовнішній агрегатор помилок (Sentry Cloud / Datadog), що ускладнює розслідування збоїв на планшетах цеху в реальному часі.

3. SPOF 3: Відсутність автоматизованого Physical Disaster Recovery Cron (DR Hazard)
Бекап зберігається у резервній таблиці Postgres, а не на незалежному S3. Відсутній автоматичний Cron вивантаження фізичних зліпків pg_dump на незалежне S3/Cloudflare R2 сховище.

---

### 4.2. Матриця технічного боргу та дорожня карта усунення

* Sentry Monitoring: Локальний кольцевий буфер. Ризик: Невідслідковані краші планшетів. Пріоритет: HIGH. Дія: Підключити реальний VITE_SENTRY_DSN для автоматичного збору стек-трейсів.
* Offsite Backup: Табличний бекап в тій же БД. Ризик: Втрата даних при збої PostgreSQL. Пріоритет: HIGH. Дія: Налаштувати cron-скрипт вивантаження pg_dump на зовнішній S3 бакет раз на добу.
* Playwright E2E: Охоплено Vitest Unit (29/29). Ризик: Приховані регресії в UI ланцюжках. Пріоритет: MEDIUM. Дія: Написати 2 E2E тести цехового циклу (Вхід -> Сканування -> Перехід -> Склад).
* Granular Table RLS: Перевірка авторизації винесена в RPC-процедури. Ризик: Потенційна можливість обходу захисту при прямому PostgREST записі. Пріоритет: MEDIUM. Дія: Додати гранулярні RLS-політики (Defense-in-Depth) на рівні PostgreSQL для таблиць work_card_history, orders та nomenclatures_v2.
* Partition Cron Automation: Партиції на 2026 рік створено вручну. Ризик: Зупинка запису при настанні нового періоду без партиції. Пріоритет: MEDIUM. Дія: Впровадити pg_cron функцію rpc_create_monthly_partitions(), яка автоматично створює нові місячні партиції на 3 місяці наперед.

## 5. Підсумковий інженерний висновок та рекомендації

### 5.1. Резюме архітектурного стану
Система CENTRUM MES v2.0 успішно пройшла рефакторинг та трансформацію до рівня Tier 1 Enterprise Production Grade з підсумковою оцінкою 9.0 / 10.

Ключові досягнення:
1. Повна ліквідація статичних секретів (x-mes-secret) та 100% перехід на персональний GoTrue JWT з хешуванням паролів bcrypt.
2. Захист мережевого периметру через Cloudflare Enterprise Edge Gateway (Origin Masking + WAF).
3. Атомарна транзакційна цілісність FSM v3 із захистом від стану гонитви через row-level lock SELECT ... FOR UPDATE та ключі ідемпотентності.
4. Висока швидкодія бази даних під навантаженням завдяки місячному секціонуванню work_card_history та частковим індексам на активні наряди (< 15 мс).
5. Повна клієнтська офлайн-стійкість (offlineQueueService), синхронізація часу (TimeSync), дебаунс сканерів (700 мс) та віртуалізація списків для цехових планшетів.

---

### 5.2. Чіткі наступні кроки для досягнення рівня 9.5+ (Pinnacle Enterprise):

1. Підключити хмарний Sentry DSN (VITE_SENTRY_DSN): Перевести sentryLogger.js із локального кільцевого буфера на зовнішній хмарний моніторинг для миттєвого відстеження помилок цехових терміналів у реальному часі.
2. Налаштувати автоматизований Offsite Physical Disaster Recovery Cron: Реалізувати щоденний автоматичний вивантажувач pg_dump на незалежний бакет S3 / Cloudflare R2 для захисту від збоїв на рівні хмарного провайдера.
3. Впровадити pg_cron для автоматичного створення партицій: Автоматизувати створення майбутніх секцій work_card_history_YYYY_MM без необхідності ручного втручання адміністратора.
4. Покрити E2E-тестами цехові сценарії (Playwright): Написати 2 автоматизованих E2E-тести для перевірки повного виробничого ланцюжка: Вхід -> Сканування -> Перехід -> Склад.
